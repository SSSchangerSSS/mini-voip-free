# 0010 — بازیابی خطاهای شبکه هنگام کنترل تماس

تاریخ: 2026-10-31

## مسئله و بازتولید

در آماده‌سازی نسخه تست دستی، پنج regression در `call_network_failure_test.dart` اجرا شدند. قبل از اصلاح، timeout پایان تماس و خطای SIP استثنای مدیریت‌نشده داشتند؛ شکست SIP مانع backstop سرور می‌شد. قطع ارتباط در accept/decline/ready نیز استثنای مدیریت‌نشده داشت و ready ناموفق دوباره ارسال نمی‌شد. مدارک قبل و بعد در گزارش manual-rc ثبت‌اند.

## تصمیم

در همان کنترل‌کننده و قرارداد موجود، خطای transport نیز مدیریت شود. SIP پایان و API پایان مستقل تلاش می‌شوند؛ UI در Ending باقی نمی‌ماند و نبود تأیید کامل به کاربر اعلام می‌شود. رد تماس، حتی با قطع API، مسیر SIP و native cleanup را تلاش می‌کند. پاسخ تأییدنشده دوباره به حالت ورودی برمی‌گردد و intent پیشین حذف می‌شود تا INVITE دیررس بدون تأیید تازه کاربر پاسخ داده نشود. ready ناموفق شبکه/502/503/504 در همان پنجره موجود با همان کلید idempotency قابل تکرار است. deadline، هویت تماس، اعتبار TLS و نسخه وابستگی‌ها تغییر نمی‌کنند.

این تصمیم تأیید قطع در سمت سرور را در زمان نبود شبکه جعل نمی‌کند. ادعای سلامت صوت فیزیکی، Push یا انتشار از آن نتیجه نمی‌شود. نسخه تست دستی 0.1.1+2 است؛ افزایش versionCode برای بررسی update بدون پاک‌کردن حساب است. امضا همچنان کلید محلی آزمایشی است.

در بازبینی تحویل، پیام قرمز «اتصال قطع شد» پس از BYE عادی نیز بازتولید شد. آزمون handshake قبل از اصلاح FAIL بود (`normal-end-before.log`). آداپتور اکنون ENDED و FAILED کتابخانه را جدا به کنترل‌کننده می‌فرستد؛ پایان عادی تماس متصل پیام شکست نمی‌سازد و شکست واقعی همچنان قابل مشاهده است. نامزد نهایی0.1.1+3 است تا از APK قبلی جدا باشد. باینری تازه دوباره روی هر دو محیط نصب و آزموده می‌شود؛ نتایج قدیمی به آن نسبت داده نمی‌شوند.

نامزد0.1.1+3 در تماس ورودی پس از شماره‌گیری ناموفق، پیام خطای قبلی را روی تماس متصل نگه داشت؛ تصویر candidate3 شاهد است. دو assertion رگرسیون پیش از اصلاح FAIL شدند. خطای پیشین در پذیرش تماس جدید، پاسخ مجدد و تأیید Connected پاک می‌شود؛ خطای واقعی جاری حذف نمی‌شود. نامزد نهایی0.1.1+4 است و شواهد نهایی جدا از نامزدهای قبلی نگهداری می‌شوند.
